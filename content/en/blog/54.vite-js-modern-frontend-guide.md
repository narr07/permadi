**Vite JS** is a modern frontend build tool and development server created by Evan You, the creator of Vue.js. It uses native ES Modules (ESM) in the browser to deliver instant server startup and ultra-fast Hot Module Replacement (HMR) updates, no matter the scale of your web application.

When building large-scale web interfaces with older generation bundlers like Webpack, initial compilation often takes tens of seconds. Every time you change a single line of code, traditional bundlers have to rebuild a massive part of the module graph before those changes appear on screen.

Vite (pronounced */vit/*, from the French word for "fast") completely overhauls this workflow. Instead of bundling all source files before the local server starts, Vite offloads module loading directly to modern browsers and only compiles files exactly when the page requests them.

## What Is Vite JS and How Does It Work?

The responsiveness of **Vite JS** comes from a strict separation between the development cycle and the production build. In older architectures, both stages were forced through almost identically heavy processing pipelines.

![Visual flow diagram showing on-demand module delivery from local server directly to browser](/article/tech-vite-js-bundler-ilustrasi.webp)

When you start the development server, Vite divides the application modules into two distinct categories:

1. **Dependencies**: Third-party libraries from the `node_modules` folder that rarely change during coding. Vite pre-bundles these libraries so thousands of small files inside an npm package turn into a single, ready-to-use module.
2. **Source Code**: The `.vue`, `.tsx`, or `.ts` component files you write and edit every minute. It serves this code directly using native ESM standards. The browser requests modules via the `<script type="module">` tag, and Vite only transforms the files currently open on the active route (on-demand compilation).

This on-demand approach keeps Hot Module Replacement (HMR) speed constant. Whether your application has ten components or ten thousand, the reload time when you hit save stays in the milliseconds range.

## Vite 8 Architectural Revolution: The Rolldown Era and Rust Ecosystem

Many tutorials on the internet still explain that Vite uses esbuild (Go-based) for development mode and Rollup (JavaScript-based) for production. That dual-bundler architecture narrative is now obsolete since the release of **Vite 8.0** in March 2026.

As Vite adoption surpasses 65 million weekly downloads on npm, maintaining two different bundling engines creates behavioral inconsistencies between the local server and the production build. To solve this, Evan You founded VoidZero and created **Rolldown**, a next-generation bundler engine based on the Rust programming language, paired with an ultra-fast parser and compiler named **Oxc**.

The shift to a single Rust architecture through Rolldown delivers immediate impacts for developer workflows:

* **Production Build Speed 10 to 30 Times Faster**: Replacing pure Rollup with Rolldown drastically cuts CI/CD build times thanks to highly efficient Rust memory management. If you want to understand why this language is so fast, you can read our review on [Rust programming memory safety and performance](/blog/rust-programming-guide).
* **Free from Data Serialization Load**: Since the parser (Oxc) and bundler (Rolldown) sit inside a unified Rust ecosystem, Vite no longer needs to pass syntax trees (AST) back and forth between Node.js processes and external binaries.
* **Full Compatibility**: Even though the engine behind the scenes completely switches to Rust, the mature Rollup plugin API remains fully supported so your project ecosystem will not break when updating versions.

Besides overhauling the core engine, Vite 7 and Vite 8 also clean up legacy support. Support for Node.js 18 ended completely following the End-of-Life (EOL) schedule as of April 2025, the Legacy Sass API was removed to switch entirely to the Modern Sass API, and the default compilation target now refers to the Baseline Widely Available standard for modern browsers.

| Comparison Aspect | Webpack (Traditional) | Early Generation Vite (v2–v5) | Modern Vite (v8+ with Rolldown) |
| :--- | :--- | :--- | :--- |
| **Dev Server Mechanism** | Bundles entire module graph upfront | Native ESM + esbuild pre-bundling | Native ESM + Oxc & Rolldown (Rust) |
| **Cold-Start Time** | Slows down as files increase | Instant (independent of file count) | Instant with a lower memory footprint |
| **Production Build Engine** | Webpack Compiler (JavaScript) | Rollup (JavaScript) | Rolldown (Pure Rust, 10–30x faster) |
| **HMR Speed** | Decreases in large-scale projects | Constant regardless of app size | Constant across all target environments |
| **Multi-Runtime Support** | Complex manual configuration | Limited to Browser & Node.js SSR | Unified via Environment API (Client, Node, Edge) |

## Environment API: Orchestrating Vue, Nuxt, and Edge Computing

Another major change modern developers must understand is the introduction of the **Environment API** since Vite 6.0 (November 2024). Previously, many developers thought Vite was only suitable for building browser-side Single Page Applications (SPA).

In reality, today's web applications rarely run in one place. When we build apps using [Nuxt JS architecture for SSR and SSG](/blog/introduction-to-nuxt-js-vue-framework-ssr-ssg), the code executes in the user's browser, on a Node.js server for Server-Side Rendering, and often on the edge network (Edge Runtime).

The Environment API turns Vite into a multi-module-graph orchestrator. Within a single development server process, Vite can manage separate module graphs for:

1. **Client Browser**: Runs standard Vue or React interface code.
2. **Node.js SSR**: Runs initial data fetching logic on the server.
3. **Edge Workers**: Executes serverless functions directly in specific environments like `workerd` from [Cloudflare Workers for serverless backends](/blog/cloudflare-workers-edge-architecture).

All these environments enjoy Hot Module Replacement simultaneously. When you change the API handler code for the Edge and a Vue interface component at the same time, both update immediately without needing to kill and restart the terminal. This capability makes Vite the core foundation for cross-language meta-frameworks like Nuxt, Astro, SvelteKit, and TanStack Start.

## How to Install Vite JS and Configure a Modern Vue Project

Starting a new project with Vite is very straightforward. Dario Benevento in his book *Frontend Development (UIUX & Psychology)* emphasizes the importance of ensuring the server-side JavaScript runtime (an active LTS version of Node.js) and a package manager like npm or pnpm are installed and verified via the terminal before initializing a frontend project.

For those of you just switching to this ecosystem and wanting to understand its basic structure first, please read our [modern Vue JS tutorial guide](/blog/modern-vue-js-tutorial).

::steps
### Initialize the Project via Terminal

Open your terminal application, then run the official scaffolding command. You can directly specify the folder name and select a TypeScript-based Vue template in a single command line:

```bash
## Using npm
npm create vite@latest my-vue-app -- --template vue-ts

## Or using pnpm (saves storage space)
pnpm create vite my-vue-app --template vue-ts
```

### Install Dependencies and Start the Dev Server

Enter the newly created project directory, install all the required packages, and then start the local server:

```bash
cd my-vue-app
npm install
npm run dev
```

In an instant, the terminal will display the local address to access your application in the browser.

### Adjust the vite.config.ts Configuration

To prepare the project for production scale, open the `vite.config.ts` file in the root directory. Add a path alias resolution (`@` pointing to the `src` folder) so component imports are not cluttered with confusing `../../` relative paths.

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import { fileURLToPath, URL } from 'node:url';

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url))
    }
  },
  define: {
    // Vue 3.4+ compile-time flag to track SSR hydration mismatch details
    __VUE_PROD_HYDRATION_MISMATCH_DETAILS__: 'true'
  },
  server: {
    port: 3000,
    open: true
  },
  build: {
    target: 'esnext',
    sourcemap: false
  }
});
```

### Test the Production Build Locally

Before uploading your code to the hosting server, always run the production compilation process and test the results using the built-in preview server:

```bash
npm run build
npm run preview
```
::

Notice the `define` property in the `vite.config.ts` code block above. Michael Thiessen explains in his book *Nuxt Tips Collection* that enabling the `__VUE_PROD_HYDRATION_MISMATCH_DETAILS__` compile-time flag is critical when running Vue or Nuxt applications in SSR mode. This setting forces Vue to print exact details about which component triggers a DOM structure mismatch between the server and the client in production mode.

## Managing Environment Variables Safely

Vite loads environment variables via `dotenv` out of the box without needing extra packages. However, it designs its security mechanism strictly so server secret keys do not leak to the public.

By default, Vite ignores all variables inside the `.env` file so they do not ship to the browser. Environment variables **must** start with the `VITE_` prefix if you want to read them inside frontend component code.

```ini
## File: .env
VITE_API_BASE_URL=https://api.permadi.dev/v1
DB_PRIVATE_TOKEN=server_secret_do_not_expose
```

Inside a Vue component or TypeScript file, call these variables through the standard ESM object `import.meta.env`:

```typescript
// Getting public variables on the client side
const endpoint = import.meta.env.VITE_API_BASE_URL;

// Evaluates to undefined in the browser for security
const secret = import.meta.env.DB_PRIVATE_TOKEN;
```

::warning
Never place backend private keys (like a payment gateway secret key or database credentials) using the `VITE_` prefix. When the build process runs, Vite statically replaces the `import.meta.env.VITE_*` text with its actual string value inside public JavaScript files that anyone can read via Inspect Element.
::

## 4 Common Vite Mistakes and Their Solutions

Switching from older bundlers to the native ESM architecture often leaves old habits that trigger errors. Here are four technical traps most commonly encountered in the field along with how to handle them.

### 1. Calling Variables with process.env

Developers used to Webpack or Create React App often type `process.env.VITE_API_URL` directly in their component code. In Vite, this immediately triggers a `ReferenceError: process is not defined` message in the browser console because the `process` object belongs to the Node.js environment, not standard browsers. To solve this, change all those calls to `import.meta.env.VITE_API_URL`.

### 2. Ignoring CommonJS Module Differences in Production

During `npm run dev` mode, the browser loads ESM modules directly. Sometimes, you install an old npm package still written in the CommonJS format (`module.exports`). That package might seem to run smoothly during development but fails to load after compilation for production. To fix this, register the legacy package in the `optimizeDeps.include` option within the `vite.config.ts` file so Vite converts it to ESM early, and make it a habit to test releases with `npm run preview`.

### 3. 404 Errors on Page Refresh in SPA Mode

When you build a Single Page Application using Vue Router and upload the `dist/` folder to static hosting services like Nginx, S3, or Apache, navigation between menus works flawlessly. However, once users hit the Refresh button on a URL like `/settings/profile`, the server immediately returns a 404 Not Found screen.

This happens because the server looks for the physical file `/settings/profile/index.html` which does not actually exist; JavaScript controls the entire routing virtually. The solution is not to change the Vite configuration, but to set rewrite rules on the hosting server to redirect all URL requests back to the main `/index.html` file.

### 4. Hydration Mismatches on Browser-Specific Components

When using Vite in an SSR framework, calling browser-specific APIs like `window.localStorage` or `document.querySelector` right in the early component cycle will break the hydration process because the `window` object does not exist on the server. Aside from enabling the hydration tracker flag in the Vite config as Michael Thiessen suggests above, make sure you separate non-SSR components using client-side isolation (like `<ClientOnly>`) or move those DOM calls into the `onMounted()` cycle.

::tip
To keep your TypeScript code structure clean and recognize data types inside `import.meta.env`, add the `ImportMetaEnv` interface definition in your project's `src/env.d.ts` file. That way, the code editor will provide autocomplete features whenever you type `.env` variable names.
::

  No. Even though Evan You (the creator of Vue.js) built it, Vite is completely framework-agnostic and is not tied to a single framework. Vite provides ready-to-use official templates for React, Preact, Svelte, Solid, as well as Vanilla JavaScript and TypeScript.

  ---
  question: Why did the official website move to vite.dev from vitejs.dev?
  ---
  The main domain shift to `vite.dev` reflects Vite's position as it grows beyond just a regular JavaScript tool into a universal build tool foundation for the modern web ecosystem under the VoidZero initiative. The old address still redirects automatically so legacy documentation links remain functional.
  :::

  :::faq-item
  ---
  question: What is the function of the npm run preview command in a Vite project?
  ---
  The `npm run preview` command starts a local static web server to run the compiled files located inside the `dist/` folder. This command helps validate the production build results before you actually upload them to a hosting provider; it is not meant to be used as a public server.
  :::

  :::faq-item
  ---
  question: Do I need to change plugin configurations when upgrading to Vite 8 which uses Rolldown?
  ---
  For most projects, no. The Rust-based Rolldown engine in Vite 8 is designed with full compatibility for the existing Vite and Rollup plugin ecosystems, so you get an immediate build speed boost without having to rewrite your `vite.config.ts`.
