**Next.js** adalah *full-stack meta-framework* berbasis React yang dikembangkan oleh Vercel untuk membangun aplikasi web modern dengan performa tinggi. Berbeda dengan React murni yang bekerja sebagai pustaka antarmuka pengguna di sisi peramban, framework ini menyediakan sistem perutean (*routing*) otomatis, optimasi aset, serta eksekusi kode langsung di lingkungan server maupun jaringan *edge*.

Saat mendampingi rekan-rekan pengembang web atau merancang aplikasi untuk kebutuhan sekolah dan bisnis, pertanyaan dasar mengenai apa itu Next.js dan bedanya dengan React murni hampir selalu muncul ketika aplikasi mulai terasa lambat serta gagal terindeks mesin pencari. Artikel ini membedah arsitektur di balik framework tersebut, mulai dari cara kerja komponen server hingga praktik terbaik pada rilis terbarunya.

## Mengapa React Murni Saja Tidak Cukup?

Dario Benevento dalam bukunya *Frontend Development (UIUX & Psychology)* menjelaskan bahwa React pada dasarnya hanyalah pustaka antarmuka pengguna yang mengandalkan *Client-Side Rendering* (CSR). Pada arsitektur *Single Page Application* (SPA) tradisional, server hanya mengirimkan satu berkas HTML kosong ke peramban beserta tumpukan kode JavaScript.

Peramban milik pengguna harus mengunduh, mengurai, dan mengeksekusi seluruh bundel JavaScript tersebut sebelum satu huruf pun tampil di layar. Pola ini memicu tiga masalah besar di lingkungan produksi:

1. **Indeksasi SEO yang Buruk**: Bot perayap mesin pencari dan *crawler* media sosial sering gagal membaca konten halaman karena elemen HTML baru terbentuk setelah JavaScript selesai dieksekusi di peramban.
2. **Waktu Muat Awal (*First Contentful Paint*) yang Lambat**: Pengguna dengan perangkat berspesifikasi rendah atau koneksi seluler tidak stabil akan menatap layar putih cukup lama saat membuka halaman pertama kali.
3. **Ukuran Bundel yang Membengkak**: Setiap pustaka pemformat tanggal, parser Markdown, atau komponen antarmuka yang Anda impor akan menumpuk dan membebani memori peramban klien.

Di titik inilah peran meta-framework menjadi krusial. Jika Anda tertarik menjaga kecepatan muat halaman agar ramah pengguna dan mesin pencari, Anda dapat mempelajari lebih lanjut tentang [panduan optimasi Core Web Vitals](/id/blog/panduan-optimasi-core-web-vitals) yang menjadi standar pengukuran performa web saat ini.

| Aspek Teknis | React Murni (SPA / Vite) | Next.js (App Router) |
| :--- | :--- | :--- |
| **Lokasi Eksekusi Utama** | Peramban Klien (*Client-Side*) | Hibrida (Server, Edge, dan Klien) |
| **Sistem Perutean (Routing)** | Manual (perlu pustaka seperti React Router) | Otomatis berbasis struktur direktori (`app/`) |
| **Kesiapan SEO & Meta Tag** | Rendah (HTML awal kosong) | Tinggi (HTML dikirim utuh dari server) |
| **Akses Database & API Rahasia** | Butuh server backend terpisah | Bisa langsung di dalam *Server Components* |
| **Ukuran Bundel JavaScript Klien** | Membesar seiring bertambahnya fitur | Minimal (kode komponen server tidak dikirim ke klien) |

## Arsitektur dan Model Rendering di Next.js

Keunggulan utama **Next.js** terletak pada kemampuannya menggabungkan empat strategi *rendering* dalam satu proyek yang sama. Mengacu kembali pada ulasan teknis Dario Benevento dalam *Frontend Development (UIUX & Psychology)*, seorang arsitek perangkat lunak kini bisa memilih metode *rendering* per halaman atau bahkan per komponen sesuai sifat datanya.

![Diagram alur rendering web dari server basis data menuju layar peramban](/article/tech-nextjs-modern-architecture-ilustrasi.webp)

### 1. Static Site Generation (SSG)
Server merender halaman menjadi berkas HTML statis satu kali saja, tepat saat proses kompilasi (*build time*). Ketika pengguna mengakses halaman tersebut, server atau jaringan *Content Delivery Network* (CDN) langsung mengirimkan HTML yang sudah jadi dalam hitungan milidetik. Pendekatan ini sangat ideal untuk halaman profil, dokumentasi, atau artikel blog.

### 2. Server-Side Rendering (SSR)
Server merender ulang halaman HTML secara dinamis setiap kali ada permintaan (*request*) masuk dari pengguna. Strategi ini memastikan data yang tampil selalu segar dan relevan pada detik itu juga, misalnya untuk halaman dasbor analitik, keranjang belanja, atau linimasa media sosial.

### 3. Incremental Static Regeneration (ISR)
ISR menggabungkan kecepatan halaman statis dengan pembaruan data dinamis. Anda dapat mengatur agar halaman statis diperbarui secara otomatis di latar belakang setelah rentang waktu tertentu atau melalui pemicu khusus, tanpa perlu membangun ulang (*rebuild*) ribuan halaman lain di seluruh aplikasi.

### 4. React Server Components (RSC) dan Streaming
Melalui arsitektur *App Router* di dalam direktori `app/`, seluruh komponen secara bawaan berjalan sebagai *React Server Components*. Komponen ini dieksekusi di server, mengambil data langsung dari basis data, lalu mengirimkan hasilnya ke peramban dalam bentuk aliran (*stream*) *payload* terkompresi. Hasilnya, kode JavaScript dari komponen server tersebut tidak pernah membebani peramban pengguna.

::note
Bagi pengembang yang lebih akrab dengan ekosistem Vue.js, konsep arsitektur hibrida dan *rendering* di sisi server ini memiliki kesamaan filosofi dengan [mengenal Nuxt JS sebagai framework Vue modern](/id/blog/mengenal-nuxt-js-framework-vue-ssr-ssg). Keduanya hadir untuk memecahkan keterbatasan SPA tradisional di ekosistem masing-masing.
::

## Evolusi Terbaru: Apa yang Berubah di Versi 15 dan 16?

Ekosistem **Next.js** bergerak sangat cepat. Jika Anda membaca tutorial lama yang masih menggunakan direktori `pages/` (*Pages Router*), banyak konsep di dalamnya sudah digantikan oleh standar baru pada siklus rilis versi 15 dan 16.

### Peralihan Penuh dari Webpack ke Turbopack
Banyak pengembang pemula hanya melihat framework ini sebagai kumpulan sintaks React. Padahal, di balik layar, fondasi kompilatornya telah bermutasi dari JavaScript murni menuju perkakas sistem berbasis bahasa pemrograman Rust, yakni SWC dan **Turbopack**. Setelah menyandang status stabil untuk mode pengembangan di versi 15, Turbopack beralih menjadi *bundler* bawaan yang menggantikan Webpack sepenuhnya di versi 16. Waktu kompilasi lokal dan *build* produksi menjadi jauh lebih singkat, terutama pada proyek monorepo berskala besar.

### Pembalikan Paradigma Caching (Opt-in Caching)
Pada rilis versi 13 dan 14, tim pengembang Vercel menerapkan kebijakan *caching* otomatis yang sangat agresif pada fungsi `fetch` dan perutean klien. Banyak pengembang mengeluh karena data di layar enggan berubah meskipun isi basis data sudah diperbarui.

Mulai versi 15 dan disempurnakan di versi 16, tim pengembang membalik paradigma tersebut sepenuhnya menjadi *uncached by default*. Permintaan `fetch`, *Route Handlers*, dan navigasi klien tidak lagi disimpan ke dalam *cache* secara diam-diam. Pengembang memegang kendali penuh secara eksplisit menggunakan standar primitif web atau menambahkan direktif `'use cache'` pada level fungsi maupun komponen yang memang ingin disimpan di memori.

### Asynchronous Request APIs dan React 19
Demi mendukung teknik *Partial Prerendering* (PPR) yang lebih efisien, seluruh API kontekstual yang bergantung pada permintaan pengguna kini bersifat asinkron. Anda wajib menggunakan kata kunci `await` saat membaca `params`, `searchParams`, `cookies()`, dan `headers()`. Selain itu, versi terbaru ini sudah terintegrasi penuh dengan fitur React 19, termasuk *Actions*, *React Compiler* (eksperimental), dan primitif *View Transitions* untuk animasi perpindahan halaman yang mulus.

## Langkah Praktis Membangun Aplikasi Next.js Modern

Bagian ini mempraktikkan konsep *App Router*, *Server Components*, dan *Server Actions* secara langsung. Anda tidak lagi perlu membuat *endpoint* API terpisah hanya untuk mengambil atau menyimpan data dari formulir.

::steps
### Inisialisasi Proyek dengan Turbopack
Buka terminal Anda dan jalankan perintah pembuatan proyek baru. Pastikan Anda mengaktifkan TypeScript, Tailwind CSS, dan App Router.

```bash
npx create-next-app@latest aplikasi-sekolah --typescript --tailwind --app --use-turbopack
cd aplikasi-sekolah
```

### Membuat React Server Component dengan Async Params
Buat berkas baru di `app/artikel/[id]/page.tsx`. Komponen ini berjalan sepenuhnya di server, mengambil data langsung dari sumber eksternal, dan merender HTML tanpa mengirimkan beban logika pengambilan data ke peramban.

```tsx
// app/artikel/[id]/page.tsx

interface PageProps {
  params: Promise<{ id: string }>;
}

async function getPostData(id: string) {
  const res = await fetch(`https://jsonplaceholder.typicode.com/posts/${id}`);
  if (!res.ok) {
    throw new Error('Gagal mengambil data artikel');
  }
  return res.json();
}

export default async function ArtikelDetailPage({ params }: PageProps) {
  // Pada Next.js 15+, params bersifat asynchronous dan wajib di-await
  const { id } = await params;
  const post = await getPostData(id);

  return (
    <article className="max-w-2xl mx-auto p-6 space-y-4">
      <h2 className="text-2xl font-bold text-slate-900">{post.title}</h2>
      <p className="text-slate-700 leading-relaxed">{post.body}</p>
    </article>
  );
}
```

### Menangani Mutasi Data dengan Server Actions
Untuk mengirim data dari formulir ke server, buat berkas `app/actions.ts`. Direktif `'use server'` di baris pertama memberi tahu kompilator bahwa fungsi ini hanya boleh dieksekusi di lingkungan server.

```ts
// app/actions.ts
'use server'

import { revalidatePath } from 'next/cache';

export async function kirimMasukan(formData: FormData) {
  const pesan = formData.get('pesan') as string;

  // Di sini Anda bisa langsung memanggil query database (Prisma / Drizzle)
  console.log('Menyimpan masukan ke database:', pesan);

  // Memperbarui cache halaman tanpa perlu memuat ulang seluruh peramban
  revalidatePath('/masukan');
}
```

### Menghubungkan Formulir ke Server Action
Sekarang panggil fungsi tersebut langsung pada atribut `action` di elemen `<form>` pada berkas `app/masukan/page.tsx`.

```tsx
// app/masukan/page.tsx
import { kirimMasukan } from '../actions';

export default function MasukanPage() {
  return (
    <form action={kirimMasukan} className="max-w-md mx-auto p-6 space-y-4">
      <label htmlFor="pesan" className="block text-sm font-semibold text-slate-800">
        Kritik dan Saran:
      </label>
      <input
        id="pesan"
        name="pesan"
        type="text"
        required
        className="border border-slate-300 rounded-md px-3 py-2 w-full"
      />
      <button
        type="submit"
        className="bg-blue-600 hover:bg-blue-700 text-white font-medium px-4 py-2 rounded-md"
      >
        Kirim Langsung ke Server
      </button>
    </form>
  );
}
```
::

## Empat Kesalahan Umum Pengembang dan Solusinya

Beralih dari pola pikir SPA tradisional menuju arsitektur hibrida server-klien sering menjebak banyak pengembang. Berikut empat kesalahan teknis yang paling sering muncul saat meninjau kode proyek:

### 1. Menaruh Direktif `'use client'` di Semua Berkas
Pengembang yang terbiasa memakai `useState` atau `useEffect` sering mengambil jalan pintas dengan menempelkan `'use client'` di bagian paling atas setiap halaman. Kebiasaan ini merusak manfaat kompresi bundel dari *React Server Components* dan mengubah aplikasi Anda kembali menjadi SPA berat.

**Solusi**: Gunakan pola *leaf-node* (ujung ranting). Biarkan halaman utama dan komponen pembungkus tetap menjadi *Server Component*. Pisahkan bagian yang benar-benar butuh interaksi klik atau *state* lokal (seperti tombol suka atau *dropdown* pencarian) ke dalam komponen kecil tersendiri, lalu berikan `'use client'` hanya pada komponen kecil tersebut.

### 2. Mengakses `params` atau `cookies()` Secara Sinkron
Banyak kode lama yang langsung memanggil `params.id` atau `cookies().get('token')` tanpa `await`. Pada versi 15 ke atas, pola sinkron ini akan memicu peringatan *runtime* atau menggagalkan proses kompilasi.

**Solusi**: Selalu jadikan fungsi komponen server Anda `async` dan gunakan *destructuring* dengan `await`, contohnya `const { id } = await params;` atau `const cookieStore = await cookies();`.

### 3. Membocorkan Logika Sensitif Server ke Komponen Klien
Karena berkas komponen server dan klien berada di dalam satu folder yang sama, pengembang terkadang tidak sengaja mengimpor modul utilitas basis data atau memanggil variabel lingkungan rahasia (seperti `DATABASE_URL` atau `API_SECRET_KEY`) di dalam berkas yang memiliki penanda `'use client'`.

::warning
Pasang paket `server-only` (`npm install server-only`) dan tambahkan `import 'server-only'` di baris pertama berkas utilitas basis data atau logika backend Anda. Dengan cara ini, **Next.js** akan langsung memblokir proses *build* jika berkas tersebut tidak sengaja terimpor ke dalam komponen klien.
::

### 4. Mengabaikan *Hydration Mismatch*
Galat hidrasi terjadi ketika struktur atau teks HTML yang dirender oleh server berbeda dengan hasil render pertama React di peramban pengguna. Kasus paling klasik adalah menampilkan waktu langsung dengan `new Date().toLocaleTimeString()` atau memeriksa objek `window` sebelum komponen terpasang (*mount*).

**Solusi**: Pastikan keluaran HTML awal selalu identik antara server dan klien. Gunakan *hook* `useEffect` untuk menjalankan logika spesifik peramban setelah komponen selesai dimuat, atau tambahkan atribut `suppressHydrationWarning` pada elemen teks tanggal yang tidak kritis.

## Implikasi Infrastruktur: Serverless dan Koneksi Database

Satu aspek krusial yang jarang dibahas dalam pengantar dasar adalah bagaimana kode **Next.js** dijalankan di server produksi. Ketika Anda mengunggah aplikasi ke platform *cloud* modern, kode di dalam folder `app/` dapat dieksekusi sebagai fungsi mikro terpisah (*Serverless Functions*) maupun di dalam kontainer Node.js yang berdiri terus-menerus (*long-running server*).

Jika Anda tertarik mendalami bagaimana komputasi tanpa server ini bekerja di jaringan global, silakan baca pembahasan mengenai [evolusi arsitektur backend edge serverless](/id/blog/arsitektur-backend-modern-edge-serverless).

Arsitektur *serverless* ini membawa konsekuensi langsung pada cara Anda menghubungkan aplikasi ke basis data:
* Saat trafik melonjak, banyak instans fungsi *serverless* dapat menyala bersamaan (*cold start*).
* Jika setiap komponen server membuka koneksi baru secara langsung, batas maksimum koneksi basis data Anda dapat cepat habis akibat *scaling serverless*.
* **Praktik Terbaik**: Selalu terapkan manajemen *connection pooling* pada ORM seperti Prisma atau Drizzle agar penggunaan koneksi basis data tetap efisien dan terkendali.

::faq
  :::faq-item
  ---
  question: Apa bedanya Next.js dengan React murni?
  ---
  React adalah pustaka (*library*) JavaScript yang hanya bertugas membangun komponen antarmuka pengguna di peramban. Next.js adalah *framework* aplikasi utuh berbasis React yang mengintegrasikan sistem perutean halaman, *rendering* di sisi server (SSR/SSG), optimasi gambar otomatis, sistem *build*, serta kemampuan menjalankan logika backend secara langsung.
  :::

  :::faq-item
  ---
  question: Kapan sebaiknya memakai Next.js dibanding Vite + React SPA?
  ---
  Gunakan Next.js jika proyek Anda menuntut SEO ketat (seperti toko daring, portal berita, atau blog), metrik *Core Web Vitals* yang optimal, proteksi logika backend di server, atau *rendering* hibrida. Jika aplikasi Anda berupa dasbor internal tertutup di balik halaman login tanpa tuntutan indeksasi mesin pencari, Vite + React SPA sering kali sudah memadai.
  :::

  :::faq-item
  ---
  question: Apakah Next.js hanya bisa di-deploy di Vercel?
  ---
  Tidak. Meskipun dikembangkan oleh Vercel dan sangat optimal di platform mereka, Next.js bersifat *open-source* dan dapat dijalankan di mana saja. Anda bebas melakukan *deploy* menggunakan Docker container, server VPS mandiri (Node.js runtime), maupun ke platform seperti Cloudflare Workers, AWS ECS, dan Google Cloud Run melalui konfigurasi output `standalone`.
  :::

  :::faq-item
  ---
  question: Apakah Next.js termasuk teknologi frontend atau backend?
  ---
  Next.js adalah *full-stack framework*. Ia menangani pembuatan antarmuka pengguna (*frontend*) dengan React, sekaligus mampu menjalankan logika *backend* melalui fitur *API Route Handlers*, kueri basis data di *Server Components*, *Server Actions*, serta *Middleware*.
  :::
::

::conclusion
Menguasai **Next.js** bukan sekadar menghafal sintaks komponen baru, melainkan mengubah cara kita membagi beban komputasi antara server dan perangkat pengguna. Jika Anda sedang merancang proyek web baru, mulailah dengan menginisialisasi proyek menggunakan *App Router* dan *Turbopack*. Biasakan menulis seluruh komponen sebagai *Server Component* secara bawaan, manfaatkan *Server Actions* untuk memangkas pembuatan *endpoint* API manual, dan sematkan direktif `'use client'` hanya pada elemen antarmuka terkecil yang membutuhkan interaktivitas peramban.
::
