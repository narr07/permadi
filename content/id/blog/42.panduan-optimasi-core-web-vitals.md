![Ilustrasi laptop dan ponsel yang menampilkan dasbor metrik performa situs web](/article/tech-core-web-vitals.webp)

**Core Web Vitals** adalah sekumpulan metrik performa standar dari Google yang mengukur pengalaman pengguna nyata berdasarkan tiga aspek utama: kecepatan muat halaman melalui Largest Contentful Paint (LCP), responsivitas interaksi lewat Interaction to Next Paint (INP), serta stabilitas tata letak visual menggunakan Cumulative Layout Shift (CLS). Ketiganya menjadi sinyal penentu peringkat pencarian dan kenyamanan pengunjung situs.

Banyak web developer masih terjebak mengejar skor 100 di Lighthouse. Mereka mengira angka hijau di layar pengujian otomatis menjamin posisi aman di mesin pencari.

Kenyataannya, halaman web yang mendapat nilai sempurna di laptop developer sering kali berstatus gagal di Google Search Console. Pengunjung di dunia nyata mengakses web memakai ponsel kelas bawah dengan sinyal seluler yang tidak stabil, bukan menggunakan jaringan fiber optik dan prosesor kencang. Untuk menjembatani kesenjangan tersebut, Anda perlu memahami cara kerja metrik lapangan ini dan menerapkan perbaikan langsung pada level kode.

## Mengapa Core Web Vitals Menjadi Standar Pengalaman Pengguna

Secara teknis, **Core Web Vitals adalah** indikator kuantitatif yang menilai apakah sebuah halaman web terasa cepat, tanggap, dan stabil di mata manusia. Google tidak menilai situs Anda dari seberapa cepat server merespons di laboratorium pengujian semata, melainkan dari rekaman telemetri jutaan pengguna browser Chrome yang terkumpul dalam Chrome User Experience Report (CrUX).

![Diagram visual tiga pilar metrik performa web yang menampilkan kecepatan, interaksi, dan tata letak](/article/tech-core-web-vitals-ilustrasi.webp)

Adam Clarke dalam bukunya *SEO 2025* menjelaskan bahwa metrik ini menggeser fokus pemilik situs dari sekadar memanipulasi kata kunci menuju perbaikan kualitas teknis yang langsung dirasakan pengunjung. Ketika halaman lambat merespons ketukan jari atau tombol tiba-tiba bergeser saat hendak diklik, pengguna akan langsung menutup tab browser.

Sejak Maret 2024, Google resmi memensiunkan First Input Delay (FID) dan menggantinya dengan Interaction to Next Paint (INP). Perubahan ini menutup celah besar pada cara developer mengukur interaktivitas. FID hanya mencatat keterlambatan pada klik pertama, sementara INP memantau latensi seluruh interaksi pengguna sepanjang sesi kunjungan mereka di halaman tersebut.

| Metrik | Fokus Pengukuran | Baik (Good) | Perlu Perbaikan | Buruk (Poor) |
| :--- | :--- | :--- | :--- | :--- |
| **Largest Contentful Paint (LCP)** | Kecepatan muat elemen visual terbesar di layar awal | ≤ 2,5 detik | 2,5 – 4,0 detik | > 4,0 detik |
| **Interaction to Next Paint (INP)** | Responsivitas layar terhadap klik, ketukan, dan tombol | ≤ 200 ms | 200 – 500 ms | > 500 ms |
| **Cumulative Layout Shift (CLS)** | Stabilitas elemen visual agar tidak bergeser mendadak | ≤ 0,1 | 0,1 – 0,25 | > 0,25 |

### 1. Largest Contentful Paint (LCP)

LCP menghitung waktu yang dibutuhkan browser untuk merender elemen visual terbesar di area layar pertama (*viewport*) sejak pengguna mulai membuka URL. Elemen ini biasanya berupa gambar banner utama (*hero image*), poster video, atau blok teks berukuran besar.

Jika server lambat merespons atau gambar utama tertahan oleh antrean unduhan CSS dan JavaScript, waktu LCP akan membengkak. Pengunjung hanya akan menatap layar putih kosong lebih lama.

### 2. Interaction to Next Paint (INP)

INP mengukur rentang waktu sejak pengguna berinteraksi (mengklik menu, mengetuk tombol keranjang belanja, atau mengetik di kolom pencarian) hingga browser berhasil menggambar pembaruan visual pada frame berikutnya. Data Web Almanac menunjukkan bahwa sekitar 35% hingga 43% situs web masih gagal memenuhi batas aman INP di perangkat seluler.

Penyebab utamanya adalah beban eksekusi JavaScript yang mengunci *main thread* browser. Saat prosesor ponsel sibuk mengeksekusi skrip pelacak atau menjalankan *rehydration* komponen antarmuka, layar akan membeku sesaat dan mengabaikan ketukan jari pengguna.

### 3. Cumulative Layout Shift (CLS)

CLS mengukur seberapa sering dan seberapa jauh elemen visual bergeser secara tak terduga saat halaman sedang dimuat. Dario Benevento dalam buku *Frontend Development* menyoroti bahwa pergeseran tata letak ini sangat merusak pengalaman pengguna. Bayangkan pengunjung berniat menekan tombol "Batal", tetapi halaman tiba-tiba terdorong ke bawah akibat banner iklan yang baru selesai dimuat, sehingga jari mereka justru menekan tombol "Beli Sekarang".

## Aturan Kelulusan Core Web Vitals Assessment dan Disparitas Data

Saat membuka PageSpeed Insights, bagian paling atas yang Anda lihat adalah status **Core Web Vitals Assessment** dengan label *Passed* (Lulus) atau *Failed* (Gagal). Aturan Google di bagian ini sangat tegas: halaman atau situs Anda hanya dinyatakan lulus apabila **ketiga metrik utama (LCP, INP, dan CLS) semuanya berada di zona hijau (Good)** pada persentil ke-75 (p75).

Persentil ke-75 berarti minimal 75% dari total kunjungan ke halaman Anda selama 28 hari terakhir harus merasakan performa di bawah ambang batas maksimal. Jika LCP dan CLS Anda sangat cepat, tetapi nilai INP berada di angka 250 milidetik (*Needs Improvement*), maka status asesmen secara keseluruhan tetap dinyatakan gagal.

::warning
Jangan menyamakan skor performa Lighthouse (0–100) dengan hasil **Core Web Vitals Assessment**. Skor Lighthouse di bagian bawah PageSpeed Insights adalah *Lab Data* yang diuji satu kali tanpa interaksi pengguna. Kelulusan resmi di Google Search Console sepenuhnya ditentukan oleh *Field Data* (CrUX) dari perangkat pengunjung asli selama 28 hari terakhir.
::

Banyak developer bingung saat mendapati skor Lighthouse 98 di komputer lokal, tetapi laporan Search Console menunjukkan ribuan URL berstatus *Poor*. Hal ini terjadi karena bot Lighthouse tidak pernah menggulir halaman ke bawah, tidak membuka menu *dropdown*, dan tidak mengklik filter produk. Di dunia nyata, saat pengguna menjalankan aksi-aksi tersebut pada ponsel kelas menengah ke bawah, skrip JavaScript yang berat akan memicu lonjakan INP dan pergeseran CLS yang hanya tercatat oleh CrUX.

## Panduan Praktis Mengecek dan Mengaudit Masalah

Sebelum mengubah baris kode apa pun, Anda harus memetakan letak sumbatan performa secara akurat. Pengecekan **Core Web Vitals** yang menyeluruh menuntut penggabungan data lapangan dan simulasi laboratorium.

::steps
### Identifikasi Klaster URL di Google Search Console
Buka dasbor Google Search Console, lalu masuk ke menu *Core Web Vitals*. Periksa tab *Mobile* terlebih dahulu karena Google menggunakan indeks berbasis seluler (*mobile-first indexing*). Cari kelompok URL yang ditandai warna merah (*Poor*) atau kuning (*Needs Improvement*) untuk mengetahui template halaman mana yang paling bermasalah.

### Jalankan Pengujian di PageSpeed Insights
Salin salah satu URL dari kelompok yang bermasalah tadi, lalu uji melalui PageSpeed Insights. Bandingkan bagian *Discover what your real users are experiencing* (data lapangan) dengan bagian *Diagnose performance issues* (data lab) untuk melihat korelasi penyebab lambatnya halaman.

### Lacak Long Animation Frames di Chrome DevTools
Buka halaman tersebut di browser Chrome, klik kanan lalu pilih *Inspect*, dan buka tab **Performance**. Aktifkan opsi *CPU throttling* ke *4x slowdown* untuk menyimulasikan prosesor ponsel, lalu rekam aktivitas saat Anda mengklik berbagai tombol di halaman. Cari blok merah bertuliskan *Long Task* atau manfaatkan API *Long Animation Frames* (LoAF) yang tersedia sejak Chrome 123 untuk melihat URL skrip dan fungsi spesifik yang menahan proses *rendering* lebih dari 50 milidetik.

### Pantau Langsung dengan Ekstensi Web Vitals
Pasang ekstensi resmi *Web Vitals* dari Chrome Web Store. Aktifkan fitur *console logging* pada pengaturannya, lalu berinteraksilah dengan elemen antarmuka web Anda untuk melihat angka LCP, INP, dan CLS berubah secara *real-time* setiap kali Anda menekan tombol.
::

## Strategi Optimasi LCP: Memangkas Waktu Muat di Bawah 2,5 Detik

Untuk memperbaiki LCP, fokuskan perhatian Anda pada dua hal: seberapa cepat dokumen HTML tiba di browser (*Time to First Byte* atau TTFB), dan seberapa cepat browser menemukan serta mengunduh aset visual terbesar.

Kesalahan paling fatal yang sering muncul pada proyek web adalah pemasangan atribut `loading="lazy"` secara menyeluruh pada semua gambar. Ketika gambar banner utama di bagian paling atas halaman diberi *lazy loading*, browser akan menunda pengunduhan gambar tersebut sampai seluruh tata letak selesai dihitung. Hasilnya, waktu LCP langsung meroket di atas 4 detik.

Matikan *lazy loading* untuk gambar utama di layar pertama, lalu berikan instruksi prioritas unduhan tertinggi menggunakan atribut `fetchpriority="high"`:

```html
<!-- Di dalam tag <head> jika gambar dimuat lewat CSS background -->
<link rel="preload" as="image" href="/article/hero-banner.avif" fetchpriority="high" type="image/avif">

<!-- Di dalam <body> untuk elemen gambar utama (LCP) -->
<img
  src="/article/hero-banner.avif"
  alt="Ilustrasi arsitektur web modern"
  width="1200"
  height="630"
  fetchpriority="high"
  decoding="async"
>
```

Jika proyek Anda dibangun di atas ekosistem Vue, Anda dapat mempelajari konfigurasi komponen gambar dan optimasi meta lebih jauh pada panduan [ Praktik Terbaik Nuxt Content dan Technical SEO](/id/blog/nuxt-content-dan-technical-seo).

Selain mengoptimalkan gambar, tekan angka TTFB server Anda. Jika situs menggunakan *Server-Side Rendering* (SSR), terapkan strategi *edge caching* agar dokumen HTML disajikan langsung dari server CDN terdekat dengan lokasi pengguna. Anda bisa membaca implementasi teknisnya pada bahasan [Panduan Cloudflare Workers untuk Backend Serverless Modern](/id/blog/arsitektur-cloudflare-workers-edge) untuk memangkas waktu tunggu respons server hingga di bawah 50 milidetik.

## Strategi Optimasi INP: Mengatasi Hydration Tax dan Long Tasks

Mengoptimalkan **Core Web Vitals** pada aspek INP adalah tantangan terbesar bagi developer frontend modern. Framework seperti Nuxt, Next, atau React memudahkan kita membangun antarmuka interaktif, tetapi membawa beban tersembunyi yang disebut *hydration tax* (pajak hidrasi).

Saat halaman SSR tampil di layar pengguna, halaman tersebut sebenarnya baru berupa HTML statis. Browser kemudian harus mengunduh bundel JavaScript dan menjalankan proses *hydration* untuk memasang *event listener* ke seluruh simpul DOM. Pada ponsel kelas bawah, proses ini sering mengunci *main thread* selama 500 hingga 1.500 milidetik. Jika pengguna mengetuk tombol menu tepat saat hidrasi berlangsung, antarmuka tidak akan merespons dan nilai INP langsung memburuk.

### Memecah Tugas Berat dengan `scheduler.yield()`

Ketika sebuah fungsi JavaScript harus memproses data dalam jumlah besar setelah pengguna menekan tombol (misalnya memfilter ratusan produk sekaligus memperbarui tampilan tombol), jangan gabungkan semuanya dalam satu eksekusi sinkron. Pecah tugas tersebut agar browser punya kesempatan menggambar perubahan visual di layar terlebih dahulu.

Hindari trik lama menggunakan `setTimeout(..., 0)` karena metode tersebut melempar sisa pekerjaan ke bagian paling belakang antrean tugas browser. Gunakan API standar web modern `scheduler.yield()` yang mengembalikan kontrol ke browser untuk merender frame, lalu langsung melanjutkan sisa fungsi Anda dengan prioritas tinggi:

```ts
async function terapkanFilterKatalog(kategori: string) {
  // 1. Berikan umpan balik visual instan ke pengguna
  tampilkanIndikatorLoading(true);

  // 2. Serahkan kontrol ke browser agar frame loading tergambar di layar
  if ('scheduler' in window && 'yield' in (window.scheduler as any)) {
    await (window.scheduler as any).yield();
  } else {
    await new Promise((resolve) => setTimeout(resolve, 0));
  }

  // 3. Jalankan komputasi berat setelah UI berhasil diperbarui
  const hasilFilter = prosesDataProdukBesar(kategori);
  renderDaftarProduk(hasilFilter);
  tampilkanIndikatorLoading(false);
}
```

### Mengurangi Beban Hidrasi dan Skrip Pihak Ketiga

Untuk aplikasi berbasis Vue yang dibahas pada artikel [Mengenal Nuxt JS: Framework Vue Modern SSR & SSG](/id/blog/mengenal-nuxt-js-framework-vue-ssr-ssg), manfaatkan fitur *lazy hydration* atau komponen *Server-Only* (`.server.vue`) untuk bagian halaman yang tidak membutuhkan interaktivitas di sisi klien. Jangan biarkan komponen di bagian bawah halaman (*below the fold*) membebani prosesor saat halaman baru saja dibuka.

Pindahkan juga skrip pihak ketiga seperti Google Tag Manager, Meta Pixel, atau widget obrolan pelanggan dari *main thread*. Anda dapat menjalankan skrip analitik tersebut di dalam *Web Worker* menggunakan pustaka seperti Partytown, sehingga aktivitas pelacakan data berjalan di latar belakang tanpa mengganggu responsivitas antarmuka utama.

## Strategi Optimasi CLS: Mengunci Tata Letak Sejak Awal

Perbaikan CLS sebenarnya paling mudah secara teknis, tetapi membutuhkan kedisiplinan dalam menulis CSS dan HTML. Prinsip utamanya hanya satu: jangan biarkan browser menebak-nebak ukuran elemen sebelum asetnya selesai diunduh.

### Tetapkan Dimensi Eksplisit dan Rasio Aspek

Selalu tuliskan atribut `width` dan `height` pada setiap tag gambar, video, dan iframe. Di browser modern, kedua atribut ini bekerja sama dengan CSS untuk menghitung rasio aspek secara otomatis dan menyediakan kotak ruang kosong yang pas sebelum file gambar selesai dimuat.

Untuk komponen dinamis seperti slot iklan, widget ulasan, atau kerangka pemuatan data (*skeleton screen*), kunci ukurannya menggunakan properti CSS `aspect-ratio` dan `min-height`:

```css
/* Memastikan gambar responsif tanpa memicu pergeseran layout */
.kartu-artikel img {
  width: 100%;
  height: auto;
  aspect-ratio: 16 / 9;
  object-fit: cover;
}

/* Mereservasi ruang untuk banner dinamis atau slot iklan */
.kontainer-banner-promo {
  width: 100%;
  min-height: 250px;
  contain: layout;
}
```

### Menangani Pergeseran akibat Web Font

Pergeseran tata letak yang halus namun sering menggagalkan skor CLS berasal dari pemuatan font kustom (*web font*). Ketika browser menampilkan teks menggunakan font sistem terlebih dahulu (*fallback font*), lalu menukarnya dengan font kustom yang memiliki tinggi baris dan lebar karakter berbeda (*Flash of Unstyled Text*), seluruh paragraf di halaman akan terdorong ke bawah.

Atasi masalah ini dengan menyamakan metrik dimensi font cadangan menggunakan properti *font descriptor override* di CSS Anda:

```css
@font-face {
  font-family: 'Plus Jakarta Sans';
  src: url('/fonts/plus-jakarta-sans.woff2') format('woff2');
  font-display: swap;
}

@font-face {
  font-family: 'Jakarta Fallback';
  src: local('Arial');
  size-adjust: 104.5%;
  ascent-override: 96%;
  descent-override: 24%;
  line-gap-override: 0%;
}

body {
  font-family: 'Plus Jakarta Sans', 'Jakarta Fallback', sans-serif;
}
```

Dengan menyelaraskan proporsi `size-adjust` dan `ascent-override` pada font lokal, pergantian ke font kustom hampir tidak akan mengubah tinggi paragraf, sehingga menjaga nilai CLS tetap di angka 0.

::tip
Setelah seluruh perbaikan LCP, INP, dan CLS dirilis ke server produksi, segera buka Google Search Console dan tekan tombol **Validate Fix** (Validasi Perbaikan) pada laporan yang bermasalah. Bersabarlah dan jangan mengubah arsitektur berulang kali dalam waktu dekat, karena Google membutuhkan waktu hingga 28 hari penuh untuk memperbarui status kelulusan berdasarkan siklus data pengguna nyata yang baru.
::

::faq
  :::faq-item
  ---
  question: Apa bedanya FID dan INP dalam Core Web Vitals?
  ---
  First Input Delay (FID) hanya mengukur waktu tunda input pada interaksi pertama saat halaman dimuat dan tidak menghitung durasi pemrosesan *event handler*. Interaction to Next Paint (INP) yang menggantikan FID sejak Maret 2024 mengukur keseluruhan latensi dari semua interaksi klik, ketukan, dan tombol sepanjang pengguna berada di halaman hingga perubahan visual benar-benar tampil di layar.
  :::

  :::faq-item
  ---
  question: Mengapa laporan Core Web Vitals di Google Search Console bertuliskan "No Data Available"?
  ---
  Status tersebut muncul karena situs atau kelompok URL Anda belum memiliki volume trafik pengguna browser Chrome yang cukup untuk memenuhi ambang batas minimum privasi dan statistik di pangkalan data CrUX. Selama trafik masih rendah, gunakan data laboratorium dari Lighthouse dan Chrome DevTools sebagai acuan perbaikan.
  :::

  :::faq-item
  ---
  question: Berapa lama waktu yang dibutuhkan hingga skor Search Console berubah setelah perbaikan?
  ---
  Perubahan status di Google Search Console dan data lapangan PageSpeed Insights memakan waktu hingga 28 hari. Dataset CrUX menghitung rata-rata performa pada persentil ke-75 menggunakan jendela agregasi bergulir (*rolling window*) selama 28 hari terakhir.
  :::

  :::faq-item
  ---
  question: Apakah lulus Core Web Vitals menjamin peringkat pertama di Google?
  ---
  Tidak secara otomatis. Metrik ini adalah bagian dari sinyal *Page Experience*. Relevansi konten dan otoritas informasi tetap menjadi penentu utama, tetapi ketika dua situs memiliki kualitas konten yang setara, situs yang lulus ujian performa ini akan diutamakan di hasil pencarian.
  :::
::

::conclusion
Memperbaiki **Core Web Vitals** bukan sekadar rutinitas mengejar angka laporan SEO, melainkan investasi teknis untuk menghargai waktu pengunjung situs Anda. Mulailah audit hari ini dengan membuka laporan Google Search Console Anda, prioritaskan perbaikan pada kelompok halaman seluler yang paling banyak mendatangkan trafik, pasang atribut `fetchpriority="high"` pada gambar utama untuk menekan LCP, gunakan `scheduler.yield()` untuk menjaga kelancaran INP, dan kunci dimensi media agar CLS tetap stabil.
::
