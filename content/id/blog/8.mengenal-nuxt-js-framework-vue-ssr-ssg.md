Mengenal Nuxt JS sebagai framework Vue modern SSR & SSG adalah langkah strategis bagi web developer yang membangun aplikasi web berskala produksi. Nuxt merupakan *meta-framework* berbasis Vue.js yang mengubah pustaka antarmuka *Single Page Application* (SPA) murni menjadi platform *full-stack* dengan dukungan *Server-Side Rendering*, *Static Site Generation*, dan *Hybrid Rendering* bawaan.

Bagi kita yang terbiasa merakit antarmuka dengan Vue, membangun aplikasi besar dari nol sering menyita waktu pada urusan konfigurasi. Kita harus memasang *router*, merancang manajemen *state*, lalu memikirkan bagaimana mesin pencari membaca konten yang dirender di peramban. Nuxt mengambil alih beban arsitektur tersebut melalui konvensi siap pakai yang terstruktur rapi.

## Mengenal Nuxt JS: Framework Vue Modern SSR & SSG

Secara teknis, Vue.js standar bekerja di sisi klien (*Client-Side Rendering*). Ketika pengguna membuka halaman web, server hanya mengirimkan file HTML kosong bersama bundel JavaScript. Peramban kemudian mengunduh, mengeksekusi skrip tersebut, dan menyusun elemen antarmuka di layar pengguna.

Pendekatan SPA murni ini kerap menimbulkan dua masalah krusial di lingkungan produksi: waktu tampil awal yang lambat pada perangkat berspesifikasi rendah dan indeksasi mesin pencari yang kurang maksimal. Nuxt menutup celah tersebut dengan menyediakan *Universal Rendering* dan mesin server terintegrasi tanpa mengubah cara kita menulis komponen Vue.

Di luar urusan rendering, Nuxt mempermudah kerja pengembang lewat tiga konvensi utama:

- **File-based Routing**: Nuxt otomatis menerjemahkan struktur file di dalam direktori `pages/` menjadi rute aplikasi lengkap dengan *code-splitting* per halaman.
- **Auto-imports**: Kita dapat langsung memanggil fungsi reaktivitas Vue (`ref`, `computed`), *composables* kustom, serta komponen antarmuka di dalam template maupun skrip tanpa barisan `import` manual.
- **TypeScript First & Vite**: Konfigurasi tipe data yang terisolasi per konteks dan *Hot Module Replacement* (HMR) cepat berbasis Vite sudah tertanam sejak kita menginisialisasi proyek.

### Evolusi Arsitektur: Dari Nuxt 3 Menuju Nuxt 4

Berbeda dengan lompatan Nuxt 2 ke Nuxt 3 yang merombak total fondasi kode ke Composition API, transisi menuju Nuxt 4 mengusung filosofi evolusi yang mulus. Tim pengembang Nuxt tidak memecah ekosistem modul dan sintaks inti, melainkan mematangkannya untuk stabilitas jangka panjang.

Pembaruan paling kentara terletak pada struktur direktori `app/` baru. Nuxt memisahkan kode sumber aplikasi (`pages/`, `components/`, `composables/`) dari file konfigurasi di akar proyek (`nuxt.config.ts`, `package.json`). Pemisahan ini merapikan ruang kerja sekaligus mempercepat kinerja *file watcher* di Vite karena IDE tidak perlu memindai ulang folder konfigurasi saat kita mengubah antarmuka.

Pada sisi manajemen data, Nuxt memperbarui lapisan *data fetching* agar mampu melakukan deduplikasi permintaan secara otomatis. Saat komponen dilepas (*unmount*), Nuxt membersihkan sisa memori (*memory leak*) secara mandiri dan menjaga ukuran sinkronisasi *state* dari server ke klien tetap ramping.

## Membedah Cara Kerja SSR, SSG, dan Hybrid Rendering

Keunggulan utama saat kita mengenal Nuxt JS sebagai framework Vue modern SSR & SSG adalah kebebasan memilih metode *rendering* yang paling selaras dengan kebutuhan produk. Kita tidak lagi terjebak pada pilihan biner antara aplikasi dinamis yang berat atau situs statis yang kaku.

### 1. Server-Side Rendering (SSR / Universal Rendering)

Pada mode SSR, setiap kali peramban meminta sebuah URL, Nuxt mengeksekusi kode Vue di sisi server terlebih dahulu. Server mengambil data dari API, menyusun markup HTML lengkap beserta *state* awal, lalu mengirimkannya ke pengguna. Peramban pun langsung menampilkan halaman utuh ke layar.

Tepat setelah HTML tampil, berlangsung proses krusial bernama **hidrasi (*hydration*)**. Pada tahap ini, peramban memuat bundel JavaScript Vue di latar belakang untuk mengambil alih elemen DOM statis tadi. Halaman yang semula hanya berupa teks dan gambar statis berubah menjadi aplikasi Vue yang reaktif dan interaktif tanpa perlu memuat ulang halaman (*full-page reload*).

### 2. Static Site Generation (SSG / Prerendering)

Mode SSG merender seluruh rute halaman menjadi file HTML, CSS, dan aset statis pada tahap kompilasi (*build time*) melalui perintah `nuxi generate`. Nuxt menyelesaikan seluruh proses pengambilan data ke database atau CMS sebelum kita mengunggah situs ke server.

Kita dapat langsung meletakkan hasil kompilasi ini di layanan CDN murni tanpa memerlukan runtime Node.js yang terus menyala. Jika Anda membangun blog dokumentasi atau situs konten berbasis Markdown, silakan baca panduan [praktik terbaik mengelola Nuxt Content dan Technical SEO](/id/blog/nuxt-content-dan-technical-seo) agar struktur meta dan skema halaman terindeks sempurna.

### 3. Hybrid Rendering dan Efisiensi Biaya Server (FinOps)

Fitur paling fleksibel pada Nuxt modern adalah **Hybrid Rendering**. Alih-alih memaksakan satu mode *rendering* untuk seluruh aplikasi, kita dapat menentukan strategi berbeda untuk setiap rute menggunakan properti `routeRules` di dalam `nuxt.config.ts`.

Dari kacamata efisiensi biaya infrastruktur (*FinOps*), pendekatan ini memangkas tagihan komputasi secara signifikan. Bayangkan sebuah platform kursus daring: puluhan ribu pengunjung melihat halaman depan dan katalog kelas, sedangkan halaman dasbor siswa berada di balik layar autentikasi login.

Jika kita memaksa seluruh aplikasi memakai SSR, server akan terus membakar siklus CPU hanya untuk merender dasbor privat yang sebenarnya tidak membutuhkan SEO sama sekali. Dengan *Hybrid Rendering*, kita bisa menerapkan *prerender* (SSG) pada halaman promosi publik, memasang *Stale-While-Revalidate* (SWR) pada katalog kelas, dan mematikan SSR (`ssr: false`) khusus untuk rute `/dashboard/**` agar berjalan sebagai SPA murni di peramban pengguna. Kombinasi ini mampu menghemat tagihan server hingga 70% karena mesin tidak perlu merender halaman privat.

| Karakteristik | SSR (Server-Side) | SSG (Static Generation) | Hybrid (routeRules) | SPA (Client-Side) |
| :--- | :--- | :--- | :--- | :--- |
| **Waktu Eksekusi Render** | Setiap ada permintaan pengguna (*request time*) | Saat proses kompilasi (*build time*) | Kombinasi per rute sesuai konfigurasi | Di peramban pengguna setelah JS diunduh |
| **Kesiapan SEO & Meta** | Sangat tinggi (HTML lengkap dari server) | Sangat tinggi (HTML statis siap baca) | Tinggi pada rute publik, hemat di rute privat | Rendah (butuh perayap yang mengeksekusi JS) |
| **Kebutuhan Infrastruktur** | Server Node.js, Deno, Bun, atau Edge Worker | Hosting statis / CDN murni | Server dinamis + integrasi CDN caching | Hosting statis / CDN murni |
| **Beban Komputasi Server** | Tinggi (proporsional dengan lonjakan trafik) | Nol saat produksi (hanya menyajikan file) | Terkendali lewat aturan cache ISR/SWR | Nol (seluruh beban di perangkat klien) |
| **Kasus Penggunaan Ideal** | E-commerce skala besar, portal berita *real-time* | Blog, dokumentasi, profil perusahaan, *landing page* | Aplikasi SaaS modern (gabungan publik & admin) | Dasbor internal perusahaan, aplikasi kasir |

## Di Balik Layar: Nitro Engine dan Dampak ke Core Web Vitals

Banyak developer hanya melihat Nuxt dari sisi antarmuka Vue, padahal rahasia ketangguhan Nuxt modern terletak pada mesin server internalnya yang bernama **Nitro**. Dibangun di atas kerangka kerja HTTP minimalis `h3`, Nitro memisahkan kompilasi logika aplikasi frontend dari lapisan adaptor server web.

Saat kita menjalankan kompilasi produksi, Nitro mengemas aplikasi beserta dependensi yang dibutuhkan ke dalam satu direktori `.output` yang mandiri (*standalone*). Kita tidak perlu lagi menyertakan folder `node_modules` penuh ke server produksi. Ukuran bundel yang ringkas ini menghasilkan waktu *cold start* yang instan.

Lebih jauh lagi, arsitektur Nitro bekerja lintas platform. Kita dapat men-deploy kode Nuxt yang sama persis ke server Node.js konvensional, Deno, Bun, hingga lingkungan *Edge Computing* seperti Cloudflare Workers (berbasis V8 isolates), Vercel Edge, dan Netlify tanpa mengubah satu baris pun logika bisnis. Jika Anda tertarik mendalami cara kerja komputasi tepi bersama basis data terdistribusi, silakan telaah bahasan [evolusi arsitektur backend Edge Serverless dan SQLite](/id/blog/arsitektur-backend-modern-edge-serverless).

### Korelasi Langsung terhadap Skor Core Web Vitals (CWV)

Standar teknis mesin pencari saat ini mengukur performa halaman secara ketat melalui metrik Core Web Vitals, terutama **LCP (*Largest Contentful Paint*)** dan **INP (*Interaction to Next Paint*)**.

Mode SSR dan SSG di Nuxt secara langsung memangkas skor FCP (*First Contentful Paint*) dan LCP. Karena server mengirimkan markup HTML siap pakai yang sudah berisi teks dan referensi gambar utama, peramban tidak perlu menunggu unduhan JavaScript selesai untuk mulai menggambar elemen terbesar di layar. Masalah layar putih kosong (*blank white screen*) khas SPA konvensional pun hilang.

Sementara itu, untuk menjaga metrik INP tetap responsif di bawah batas aman 200 milidetik, Nuxt menyediakan fitur *Islands Architecture* melalui komponen `<NuxtIsland>`. Fitur ini memungkinkan kita merender komponen berat secara eksklusif di server dan hanya mengirimkan HTML statisnya ke klien. Hasilnya, beban eksekusi JavaScript di *main-thread* peramban berkurang drastis sehingga antarmuka selalu sigap merespons interaksi pengguna.

## Panduan Praktis Membangun Proyek Nuxt Modern

Mari kita terapkan konsep arsitektur di atas ke dalam proyek nyata. Kita akan menginisialisasi proyek, mengatur strategi *Hybrid Rendering*, dan mengambil data API dengan pola yang aman.

::steps
### Inisialisasi Proyek dengan Nuxi CLI

Pastikan lingkungan kerja Anda telah memasang Node.js versi LTS terbaru. Buka terminal dan jalankan alat baris perintah resmi `nuxi` untuk mengunduh kerangka dasar Nuxt:

```bash
## Membuat scaffold proyek Nuxt baru
npx nuxi@latest init my-nuxt-app

## Masuk ke direktori proyek dan pasang dependensi
cd my-nuxt-app
npm install

## Menjalankan server pengembangan lokal
npm run dev
```

Setelah proses instalasi selesai, Anda dapat mempercepat pembuatan antarmuka dengan mengikuti [panduan membangun antarmuka cepat dengan Nuxt UI](/id/blog/nuxt-ui-panduan-desain-modern) yang sudah terintegrasi penuh dengan Tailwind CSS dan TypeScript.

### Konfigurasi Hybrid Rendering di nuxt.config.ts

Buka file `nuxt.config.ts` di akar proyek Anda. Di sini kita mendefinisikan `routeRules` untuk mengatur bagaimana Nuxt merender dan menyimpan setiap kelompok URL di dalam memori cache:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  ssr: true, // Mengaktifkan kemampuan server-side secara global

  routeRules: {
    // 1. Halaman utama & profil dirender statis saat build (SSG)
    '/': { prerender: true },
    '/about': { prerender: true },

    // 2. Artikel blog memakai SWR: disajikan instan dari cache,
    // lalu diperbarui di latar belakang setiap 1 jam (3600 detik)
    '/blog/**': { swr: 3600 },

    // 3. Halaman admin menggunakan SPA murni (menghemat beban server)
    '/admin/**': { ssr: false },

    // 4. Endpoint API internal dengan cache selama 10 menit
    '/api/products': { cache: { maxAge: 600 } }
  }
})
```

### Pengambilan Data Aman dengan useFetch

Buat sebuah halaman dinamis di `pages/blog/[slug].vue`. Gunakan *composable* bawaan `useFetch` untuk mengambil data dari endpoint internal maupun eksternal agar aplikasi terhindar dari pemanggilan ganda saat hidrasi:

```vue
<!-- pages/blog/[slug].vue -->
<script setup lang="ts">
const route = useRoute()
const slug = route.params.slug

// useFetch mengeksekusi permintaan di server dan meneruskan datanya
// ke klien melalui payload hidrasi secara otomatis
const { data: post, pending, error } = await useFetch(`/api/posts/${slug}`, {
  key: `post-${slug}`,
  lazy: false
})
</script>

<template>
  <main class="container">
    <div v-if="pending">Memuat konten...</div>
    <div v-else-if="error">Terjadi kesalahan: {{ error.message }}</div>
    <article v-else-if="post">
      <h1>{{ post.title }}</h1>
      <div v-html="post.content"></div>
    </article>
  </main>
</template>
```
::

Untuk skenario aplikasi yang membutuhkan pengelolaan basis data, autentikasi, serta integrasi rute server yang lebih kompleks di dalam folder `server/api/`, Anda dapat mempelajarinya lebih lanjut di artikel [arsitektur backend dan integrasi modern Nuxt](/id/blog/arsitektur-backend-dan-integrasi-nuxt).

## Tiga Jebakan Umum Developer Saat Menggunakan Nuxt

Ketika beralih dari Vue SPA ke lingkungan *Universal Rendering* di Nuxt, perbedaan siklus hidup kode kerap menjebak pengembang. Nuxt kini mengeksekusi kode di dalam `<script setup>` pada dua tempat berbeda: lingkungan server Node.js atau Edge dan lingkungan peramban pengguna.

### 1. Hydration Mismatch Error

Kesalahan ini muncul ketika struktur HTML yang dihasilkan server berbeda dengan struktur DOM yang dihitung Vue di peramban pada saat render pertama. Penyebab paling sering adalah pemanggilan objek spesifik peramban seperti `window`, `localStorage`, atau pemformatan waktu lokal `new Date().toLocaleDateString()` secara langsung di template. Server dan perangkat pengguna bisa saja berada di zona waktu yang berbeda.

::warning
Jangan pernah memanggil `window` atau `localStorage` langsung di badan utama `<script setup>`, karena objek tersebut tidak ada di lingkungan server Node.js dan akan menghentikan proses SSR.
::

Sebagai solusinya, pindahkan logika spesifik peramban ke dalam *lifecycle hook* `onMounted()` yang hanya berjalan di sisi klien, atau bungkus komponen terkait dengan komponen bawaan `<ClientOnly>`:

```vue
<template>
  <ClientOnly>
    <template #fallback>
      <p>Memuat profil...</p>
    </template>
    <UserProfile />
  </ClientOnly>
</template>
```

### 2. Double Fetching (Panggilan API Ganda)

Pengembang yang terbiasa memakai `fetch()` standar JavaScript atau pustaka `axios` langsung di tingkat atas `<script setup>` akan mendapati API mereka dipanggil dua kali untuk satu kunjungan halaman: satu kali saat server merender HTML, dan satu kali lagi saat peramban melakukan hidrasi.

Selalu gunakan `useFetch()` atau `useAsyncData()` saat mengambil data awal komponen. Kedua *composable* ini menyematkan hasil respons server ke dalam objek payload internal `__NUXT__`. Ketika peramban melakukan hidrasi, Nuxt cukup membaca data dari payload tersebut tanpa menembak ulang endpoint API.

### 3. Salah Memilih Perintah Build untuk Target Hosting

Kesalahan klasik lainnya terjadi saat tahap *deployment*. Pengembang menjalankan perintah `nuxt build` (mode SSR atau Hybrid dinamis), tetapi mengunggah hasilnya ke layanan hosting statis murni seperti GitHub Pages atau bucket S3 standar. Akibatnya, situs gagal berjalan dan hanya menampilkan pesan *404* atau layar putih kosong.

::tip
Sesuaikan perintah kompilasi dengan infrastruktur Anda: gunakan `npx nuxi generate` jika menargetkan hosting statis murni (GitHub Pages, S3, Firebase Hosting), dan gunakan `npx nuxi build` jika menargetkan lingkungan Node.js, VPS, Docker, atau Edge Serverless seperti Cloudflare Workers dan Vercel.
::

::faq
  :::faq-item
  ---
  question: Apakah Nuxt JS menggantikan fungsi Vue JS?
  ---
  Tidak. Nuxt dibangun tepat di atas fondasi Vue. Nuxt menyediakan arsitektur aplikasi seperti routing otomatis, SSR, optimasi bundel, SEO, dan mesin server API, sedangkan penulisan komponen, sistem reaktivitas (`ref`, `reactive`), dan sintaks template tetap 100% menggunakan standar Vue 3.
  :::

  :::faq-item
  ---
  question: Kapan saya harus memilih SSR dibanding SSG di Nuxt?
  ---
  Pilih **SSG** bila konten jarang berubah atau diperbarui melalui pemicu *webhook* CMS, seperti pada situs dokumentasi, portofolio, dan *landing page*. Pilih **SSR** bila konten sangat dinamis, membutuhkan personalisasi berbasis sesi atau cookie pengguna, atau memiliki jutaan halaman katalog *e-commerce* yang tidak praktis dikompilasi satu per satu saat proses *build*.
  :::

  :::faq-item
  ---
  question: Apa perbedaan utama antara $fetch dan useFetch di Nuxt?
  ---
  `$fetch` adalah klien HTTP berbasis pustaka *ofetch* untuk melakukan mutasi data atas interaksi pengguna di peramban, misalnya mengirim formulir POST saat tombol diklik. Sementara itu, `useFetch` adalah *composable* pembungkus khusus untuk siklus hidup rendering SSR agar data dari server otomatis diteruskan ke klien tanpa memicu panggilan ganda (*double request*).
  :::

  :::faq-item
  ---
  question: Apakah Nuxt 3 dan Nuxt 4 sulit dipelajari oleh pemula?
  ---
  Justru lebih mudah dibanding framework ekosistem lain bagi pemula yang sudah memahami dasar Vue. Fitur *Auto-imports* (tidak perlu mengimpor `ref` atau `computed` secara manual) dan *File-based Routing* memangkas banyak kode *boilerplate*, sehingga Anda bisa langsung membuat halaman baru cukup dengan menambahkan file `.vue` di dalam folder `pages/`.
  :::
::

::conclusion
Mengenal Nuxt JS sebagai framework Vue modern SSR & SSG memberi kita kendali penuh atas performa, keterbacaan mesin pencari, dan efisiensi biaya server dalam satu ekosistem terpadu. Sebagai panduan langkah berikutnya untuk proyek Anda:

- **Gunakan SSG (`nuxi generate`)**: Jika Anda sedang membangun blog, situs dokumentasi, atau *landing page* yang menuntut waktu muat cepat di layanan CDN statis tanpa biaya server dinamis.
- **Gunakan SSR (`nuxi build`)**: Jika Anda mengembangkan aplikasi *e-commerce* dinamis atau portal berita dengan jutaan halaman yang datanya berubah setiap saat dan membutuhkan personalisasi sesi.
- **Terapkan Hybrid Rendering (`routeRules`)**: Jika aplikasi Anda menggabungkan halaman publik yang butuh SEO kuat sekaligus halaman dasbor autentikasi privat, sehingga beban komputasi server tetap hemat dan skor Core Web Vitals terjaga optimal.
::
